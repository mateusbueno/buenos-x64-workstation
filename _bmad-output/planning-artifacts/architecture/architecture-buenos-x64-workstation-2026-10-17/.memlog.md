- (decision) [ADOPTED] Paradigm: single-writer control plane + realtime data plane. Inside engine process, one non-RT control thread is the only writer of performance/patch state; RT thread receives immutable snapshots via atomic pointer swap and commands via lock-free SPSC queues; UI, MIDI, desktop app, sequencer are clients sending commands. Prevents: two owners of patch state, RT thread doing parse/alloc/locks, UI crash losing sound
- (decision) Process topology: engine (control thread + RT audio threads + streaming I/O threads with io_uring and AES decrypt), ui (touch + panel, client only), librarian (import/convert/compress/encrypt/index, desktop-app service, low priority off audio cores), sysd under systemd (A/B updates, USB gadget UAC2/MIDI/app protocol, power, logs). Prevents: import crash or heavy CPU affecting sound; streaming across process boundaries
- (decision) Content keys are unwrapped from OP-TEE into engine memory while a library is loaded (in-TEE decrypt too slow for 256 voices); acceptable under deter-not-unbreakable goal given secure boot
- (decision) State ownership split: structural state (stored patch: programs, parts, splits, FX routing, save) owned by control thread via snapshots; performance state (notes, velocity, drawbars, knobs, pedals, pitch bend, CC) owned by RT thread via timestamped lock-free event queue applied next block; RT publishes performance changes on an outbound queue that control mirrors for UI and save. Prevents: UI showing one value while sound plays another; snapshot churn on continuous controls
- (decision) Single internal event format: MIDI 2.0 UMP with timestamps for keybed, DIN MIDI, USB MIDI and panel; keybed reader is a small RT thread in engine reading MCU over UART/SPI, bypassing control thread
